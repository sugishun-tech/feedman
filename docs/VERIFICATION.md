### GUIビルド検証についての制約

この実行環境には **GTK 3 / GLib のランタイムはありましたが、開発ヘッダーとGTKのpkg-configファイルがありませんでした**。そのため、ここでのGUI確認には公開ABIに対応した検証専用の最小宣言を別ディレクトリーに用意し、実際のGTKランタイムへリンクして、Xvfb上でウィンドウを起動・操作しました。

**通常のGTK開発パッケージを使ったデスクトップ版のフルビルドと、GitHub Actions上での実行は、この環境では未実施です。** それらの成功を確認済みとはしていません。配布するプロジェクトは標準の `<gtk/gtk.h>` と `pkg-config gtk+-3.0` を使用します。検証専用の代替宣言や実行ファイルは同梱していません。

READMEの開発パッケージを導入した環境で通常のCMakeビルドを行い、公開前に同梱CIの結果も確認してください。画面画像はモックアップではなく、このGTKランタイム上で起動した実アプリのスクリーンショットです。表示記事は架空のデモデータです。

## 速度測定

`feedman_tests --benchmark` のローカルHTTPサーバーを使用しました。外部ネットワーク、元Python版、実サイトのRSSは測定対象にしていません。

| 条件 | 内容 |
|---|---|
| フィード数 | 16 |
| 各HTTP応答の人工遅延 | 150ms |
| 記事数 | 各20記事 / 合計320記事 |
| 保存先 | 各測定で新しいSQLiteデータベース |
| キャッシュ | 新規取得。304によるスキップは比較に含めない |
| ビルド | C版 Release |
| 回数 | 各条件1回。統計的な信頼区間は算出していない |

| スレッド数 | 取得・解析・保存の合計時間 | 保存件数 |
|---:|---:|---:|
| 1 | 2.416598秒 | 320 |
| 8 | 0.311147秒 | 320 |

この条件では **7.767倍**。生の値は [benchmark-result.json](benchmark-result.json) にあります。遅延を並列に待てることを確認する測定であり、Cへ移植したこと自体の寄与や、実サイトでの高速化倍率を分離した測定ではありません。

別のHTTPテストでは、複数リクエストが実際に同時進行していること、初回160記事保存後に同じ8フィードを再取得するとすべて304となり本文受信量が0になること、保存件数が増えないことも検証しています。

マウス操作後の実保存値は [mouse-test-result.json](mouse-test-result.json) にあります。初期値からカレンダーの右境界、検索欄の下境界、一覧/本文の境界を動かし、保存ファイルを読み直して位置変更を確認しました。

## 未検証・対象外

インターネットへの接続が使えない環境のため、実サイトへの接続成功、実サーバーのTLS・HTTP/2・圧縮応答、配信元ごとのレート制限は未検証です。実装上はlibcurlの機能を利用しますが、ローカルHTTPテストと実サイトでの相互運用確認を同一視していません。

Wayland上の操作、Windows / macOS、スクリーンリーダーとの組合せ、異なるデスクトップテーマ、実ブラウザーへのリンク引渡し、数百万記事規模、ThreadSanitizer、網羅的ファジング、長期間の連続稼働は未検証です。フォールバック検索を確認しましたが、既存FTS付きDBをFTS5機能自体のないSQLiteへ移すケースは対象外です。

元のmyrssの全機能・HTML表示との完全な互換性は主張しません。旧JSON取込と公開日での閲覧は保持し、取得日は初回保存日を正しく別管理する設計へ変更しています。
